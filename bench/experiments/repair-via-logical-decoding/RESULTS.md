# Scenario 2, Matrix-shaped: does logical decoding report what a corrupt-index DELETE really removed?
Script: `run.sh`. Reproduce with `make -C bench setup && bench/collectors/cdc/up.sh && bench/experiments/repair-via-logical-decoding/run.sh`.
**Status of this file: four registered runs made (run-1 to run-4) after one discarded run; results and verdicts are in the sections after the hypotheses.** The hypotheses were committed (`ee03758`) before any run and their text and thresholds were not edited afterwards; `git diff ee03758 -- RESULTS.md` shows exactly what was added (this status line, and everything after the hypotheses section).
## What this is, and what it is not
This is a lab approximation of the SHAPE of a real incident, not a reproduction of it. The shape, taken from the public postmortem of the Matrix.org incident of June and July 2025 (`docs/research/p0-public-postmortems.md`, incident 2): a corrupt PostgreSQL index made a clean-up job delete rows of other rooms than the ones it targeted, because the index entries of the targeted state group pointed at heap space that held rows of another state group. We cannot reproduce Matrix's actual corruption mechanism (what damaged their 4 TB index, on what hardware or version, over what year). What this experiment builds is an index whose entries point at heap positions holding rows of other keys, which is the effect the postmortem describes, made by a different and deliberate method (below). Nothing here is a statement about Matrix's stack, schema, volumes or recovery.
The claim under test is ours, not Matrix's. `docs/research/p0-public-postmortems.md` reasons, and marks as "plausible, not proven", that logical decoding would have reported the rows actually deleted even though the index that drove the DELETE was wrong, because the WAL records the heap tuple removed and not the planner's intent. `docs/research/STATUS.md` lists this as only our reasoning. This experiment checks that one sentence on PostgreSQL.
## How the fault is engineered (and what that approximates)
Method: swap in a donor index at file level, on a stopped server, in a throwaway PostgreSQL 16 pod.
1. Five tables with the same columns, 2,000 rows each, inserted in `id` order into fresh tables so that heap position follows `id`. Columns: `id int primary key`, `state_group int`, `event_id text`, `depth int`, `amount numeric(12,2)`, `ts timestamptz`, `content text` (about 160 characters). Each has a plain btree index on `state_group`, the key a "clean-up job" deletes by.
2. The **donor** table has the clean layout: `state_group = (id-1)/10 + 1`, 200 groups of 10 consecutive rows.
3. The four **experiment** tables have a *shifted* heap: `state_group = ((id-1+SHIFT)/10) % 200 + 1` with `SHIFT = 5` (half a block, so each group straddles two blocks of positions) in runs 1 to 3 and `SHIFT = 370` (a whole 37 groups, so the heap positions of group K hold group K+37) in run 4. Two use `REPLICA IDENTITY FULL` and two the default (primary key only). In each pair one table is *corrupted* and one is a healthy *control*.
4. With the server stopped cleanly, the donor's index file is copied over the `state_group` index file of the two corrupted tables. The server is restarted. The index of a corrupted table now says "group K is at heap positions (K-1)*10+1 to K*10", which is true for the donor and false for the table. The controls keep the index PostgreSQL built.
What this approximates: the effect "index entries point at heap space holding another entity's rows" (a stale index, or heap reused under it). What it is not: a bit flip, a collation or glibc change, a storage fault, or a bug in index maintenance. The fault is deliberate, applied by file copy on a server that was stopped cleanly, and it is a *clean* inconsistency: the index is structurally valid btree and only disagrees with the heap. A real corruption may also be structurally broken, or inconsistent in a way that makes the DELETE or the decoding error out; that is not covered.
Safety: the pod, its data directory, its slot and its tables are throwaway and named `sc2-*` / `sc2_*`. `bench-postgres` and `bench-cdc` are not written to. Nothing is done to any index other than the ones in the throwaway cluster.
## The incident, and the ground truth that does not use the index
The "clean-up job" is `DELETE FROM t WHERE state_group = ANY (ARRAY[10, 60, 110])`, run with `enable_seqscan = off` and `enable_bitmapscan = off` so that it is driven by the index; `EXPLAIN` must show an Index Scan on the `state_group` index, and the index's `idx_scan` counter must rise during the run with the table's `seq_scan` unchanged.
Ground truth, taken without the index: (i) before the DELETE, a copy of every table made by a sequential scan of the heap (`enable_indexscan = off`, `enable_bitmapscan = off`), including every column; (ii) the *intended* set: ids whose heap `state_group` is in the target list, from that same snapshot; (iii) the *removed* set: the rows returned by the DELETE's own `RETURNING *` (what the executor removed), checked against the snapshot minus a sequential scan of the table after the DELETE. The events are never used to build the ground truth.
## Pre-registered hypotheses (written before the first run)
Definitions. *Intended*: ids whose heap `state_group` is a target group. *Removed*: ids the DELETE actually removed. *Foreign*: removed ids whose heap `state_group` is not a target group. *Missed*: intended ids not removed. *Event set*: for a table, the Debezium events with `op = d` received for it after the DELETE. *Before image*: the `before` object of such an event. Rows are compared by value after normalising types (`numeric` as a decimal, `timestamptz` as an instant).
- **H1, the fault is real and the DELETE is index-driven. If this fails in a run, that run is INCONCLUSIVE, not a failure of logical decoding.** In each run: (a) the PostgreSQL `amcheck` function `bt_index_check(index, heapallindexed => true)` raises an error on both corrupted indexes and returns without error on both control indexes; (b) `EXPLAIN` of the DELETE shows an Index Scan on the `state_group` index (and no Seq Scan or Bitmap Heap Scan) on all four tables, and the index's `idx_scan` rises by at least 1 with `seq_scan` unchanged; (c) on the corrupted tables the removed set differs from the intended set with at least 1 foreign row and at least 1 missed row, and the expected counts hold: 30 removed, 15 foreign and 15 missed with `SHIFT = 5`; 30 removed, 30 foreign and 30 missed with `SHIFT = 370`; (d) on the control tables removed equals intended (30 rows, 0 foreign, 0 missed). *Falsified in a run if* any of (a) to (d) fails.
- **H2, with `REPLICA IDENTITY FULL`, the events are the removed rows with their exact prior content, on the corrupted table.** The event set has exactly one event per removed row and none for any other row (the set of before-image ids equals the removed set, no duplicates); and every before image equals the pre-incident snapshot row of that id in every column, with 0 mismatching columns; the foreign rows are among the events and the missed rows are not. *Falsified in a run if* any of these fails.
- **H3, with the default identity, the events identify the removed rows exactly but carry only the key.** On the corrupted table with the default identity: the set of key values in the events equals the removed set (one event per removed row, none for any other row); every non-key column of every before image is null or absent. The second part is a prediction about what the default identity gives, written down so that the verdict does not blur it: under the default identity the *prior content* of the row is not in the event. *Falsified in a run if* the key set differs from the removed set, or any non-key column of a before image holds a value.
- **H4, the controls behave the same way.** On both control tables (healthy index), H2 (for the `FULL` one) and H3 (for the default one) hold with the same criteria. If H4 failed while H2 and H3 held, the corrupt-index result would still stand but would not be shown to be about the corruption; if H4 failed in the other direction it would point at the harness. *Falsified in a run if* either control fails its criteria.
- **H5, the before images are enough to repair the damage in the `FULL` tables.** Re-inserting the before images of the event set into a copy of the post-incident table (made by a sequential scan) yields a table with 0 rows differing from the pre-incident snapshot (all columns), on the corrupted `FULL` table and on its control. *Falsified in a run if* any row differs.
- **H6, one transaction.** For every table the event set carries a single `txId`, equal to the `txid_current()` of the transaction that ran the DELETE, and the total number of delete events received over the four tables is exactly the total removed (120 with the counts above), with no other event after the slot started. *Falsified in a run if* any of these differ.
- **H7, reproducibility.** The H1 to H6 outcomes and the counts are the same in all runs, with at least 3 valid runs (a run that fails H1 or whose stream is incomplete is not valid but is reported). *Falsified if* any valid run differs from the others in an outcome or a count.
Verdict rule, fixed in advance. The specific claim is: "logical decoding correctly reports deleted rows' prior content even when the index that selected them was corrupted."
- **PASS** for a replica-identity mode if H1 held in at least 3 runs and the mode's criteria (H2 for `FULL`; for the default identity, the identification half of H3) held in all valid runs, on the corrupted table and on its control.
- **FAIL** if, in any valid run (H1 held), the event set differs from the removed set or a `FULL` before image differs from the snapshot.
- **INCONCLUSIVE** if fewer than 3 runs are valid.
- The word "prior content" is judged separately: under the default identity, if H3 holds, the claim about *prior content* is reported as **not applicable by design** (the event identifies the row; it does not carry its content), not as PASS.
A run whose harness fails (a pod does not start, the stream is incomplete) is reported as such, not dropped. A hypothesis that fails in any run is reported as failed.
Setup details these refer to, so that nothing is fitted later: PostgreSQL 16 in a throwaway pod, `wal_level = logical`, `pgoutput`, Debezium Server 3.6.3 through the Debezium Operator with its own slot, `decimal.handling.mode = string`, JSON without schema, `snapshot.mode = no_data`, tombstones off, the four experiment tables in a filtered publication, the connector started *after* the index swap and the server restart and *before* the DELETE.

## What was run
- **Cluster:** kind (`db-sensor-bench`), PostgreSQL 16.15 (aarch64) in a throwaway pod `sc2-pg` with `wal_level = logical` and autovacuum off, Debezium Operator 3.6.3 with a probe `DebeziumServer` `sc2-probe` (slot `sc2_probe`, `pgoutput`, Debezium Server 3.6.3), an HTTP sink to a pod `sc2-receiver` that appends every event to a file. `bench-postgres` and `bench-cdc` were not written to. Everything created was named `sc2-*` / `sc2_*` and removed at the end of each run; checked after the last run: no `sc2` pod, service, configmap or `DebeziumServer` left (the slot and the tables lived in the pod's own data directory and went with it).
- **Run date:** 2026-11-11 (the container clock). Four registered runs, harness 13 of 13 checks passed in each: run-1, run-2, run-3 with `SHIFT = 5`; run-4 with `SHIFT = 370`. Each run builds a fresh cluster from scratch, so the four are repetitions of a deterministic construction on fresh instances, not independent samples.
- **Per run:** four tables of 2,000 rows, 30 intended rows (3 groups of 10), 30 rows removed per table, 120 delete events in total. Index files are 40,960 bytes for all five indexes (the donor and the four), so the file copy was a like-for-like swap. Before the swap, `bt_index_check(..., heapallindexed => true)` passed on all five indexes (5 of 5 checks passed in each run).
- **Discarded run.** One earlier run (kept as `raw/discarded-1/`) was made with the harness as first written. It reached the same counts but my harness read `seq_scan` after its own post-incident verification dump, which adds one sequential scan to each table, so H1(b) read "seq_scan unchanged" as false on all four tables. That is a bug in my measurement, not a property of the DELETE (the `EXPLAIN` in that run already showed Index Scan). I moved the stats read before the dumps (commit after `429dc2f`), moved the run to `discarded-1` and ran the four registered runs. I also added, to `analyze.py` after seeing that run, a count of what the default-identity before-image values are (placeholders or real values); it does not enter any hypothesis. Hypotheses and criteria were not touched. Note that the discarded run's `metrics.json` was regenerated by the final `analyze.py` and says `run-1` in its header; the registered runs are the four in `raw/run-*`.

Every row above was the same in every run of its SHIFT.
- **The fault was effective and the DELETE was index-driven.** On the corrupted tables `amcheck` raised `heap tuple (0,6) from table "..." lacks matching index tuple within index "..."` (runs 1 to 3; `(0,1)` in run 4). `EXPLAIN` showed `Index Scan using <table>_grp_idx` with `Index Cond: (state_group = ANY ('{10,60,110}'::integer[]))` under the Delete node on all four tables in all four runs, with no Seq Scan or Bitmap Heap Scan. The index's `idx_scan` rose by 3 and `seq_scan` by 0 on every table (3, not 1, because PostgreSQL counts one index scan per array element).
- **What the corrupt index did.** With `SHIFT = 5`, each target group K lost the 5 rows at the front of the index's block of positions (rightly) and also 5 rows of group K+1 (wrongly), and left 5 rows of group K in the heap (the last 5 positions of the previous block). Foreign rows were of groups 11, 61 and 111. With `SHIFT = 370` all 30 removed rows were foreign (groups 47, 97, 147) and all 30 intended rows survived. The removed set was confirmed two ways without the index: the DELETE's own `RETURNING *` equalled the set `pre-snapshot minus post-incident seqscan` in all 16 table-runs, and every `RETURNING` row equalled its pre-incident snapshot row.
- **The events matched the removed rows, not the intended ones.** In all 16 table-runs the delete events were exactly one per removed row (the before-image ids equal the removed ids, no duplicates, none for a missed row), including the foreign rows of the other groups. The total was 120 events in each run, no other event, and every table's events carried the one `txId` of the DELETE's transaction (757, 758, 759, 760 in every run, equal to `txid_current()` printed by the DELETE session).
- **With `REPLICA IDENTITY FULL`, the prior content was exact.** 210 cells per table (30 rows by 7 columns) compared with the pre-incident seqscan snapshot, 0 mismatches, in both the corrupted and the control table, in all four runs (`numeric` compared as a decimal and `timestamptz` as an instant). Re-inserting the before images into a seqscan copy of the post-incident table gave 0 rows differing from the pre-incident snapshot (2,000 rows), for the corrupted and the control table, in all four runs.
- **With the default identity, the event identified the right rows but did not carry null non-key columns.** The key (`id`) was right in all 30 events per table. The other six columns of every before image were not null: 180 values per table (30 events by 6 columns), and all 180 equal the *type default* of a `NOT NULL` column (`0`, empty string, `0.00`, `1970-01-01T00:00:00Z`), not the row's prior value. 5 of the 180 happen to equal the true value (the `depth` of rows whose real depth was 0). Zero values were neither the placeholder nor the true value. This is the same on the corrupted and the healthy table, so it is a property of the default identity with `NOT NULL` columns on this connector, not of the corruption.

## What this supports
- In this lab, a DELETE that was driven by an index that disagreed with the heap removed rows of the wrong group, and the logical-decoding events reported the rows that were actually removed, not the rows the predicate named. The "victim list" of such an incident (including the collateral rows of other groups) can be read from the events by key. With `REPLICA IDENTITY FULL` it can also be read with the full prior content, and re-inserting those images restored the table exactly. That is the one sentence in `p0-public-postmortems.md` and `STATUS.md` that was only our reasoning; for this fault shape, this PostgreSQL version and these two identity modes, it now has a measured result behind it.
- The mechanism is the expected one, and the experiment is consistent with it: the WAL delete record names the heap tuple removed, and the walsender reconstructs the key (or the whole old row) from that tuple, so the index that led there does not enter the event. The result does not prove that mechanism; it only did not contradict it in these 16 table-runs.
- The control tables behaved identically, so the corrupt-index runs are not special cases of the harness.
## What did not go as predicted, or needs a caution
- **H3's second clause failed.** I predicted that non-key columns of a default-identity before image would be null or absent. They were type-default placeholders (180 of 180). My tables had only `NOT NULL` columns; I did not test nullable columns, so I do not know what a nullable column shows (likely null, but not run) and I do not claim it. The verdict statement above is split so that this is not blurred.
- **H4 failed through the same clause**, and is reported as failed; it does not change the corrupt-versus-healthy comparison.
- The two shifts are two geometries of the same method. Real corruption would not be that regular.
- All ground truth that mattered here (`RETURNING`, the seqscan snapshots) came from the same engine that produced the events. An engine bug that affected both the executor's view and the WAL would not be seen.
- Foreign rows were fully removed and logged; the "missed" rows (intended but still present) correctly produced no event. That is the point, and also a reminder that the stream can only report what happened; it cannot tell you what the job meant to delete.

## Not covered, and not claimed
(Written before the runs; extended after them.)
- Matrix's actual corruption, stack, volumes, or recovery. The corruption here is an engineered approximation of one effect, and a different one from whatever damaged their index.
- Detection of the incident. The experiment starts at the DELETE; nobody had to notice that rows were missing.
- A corrupted index that breaks the statement or the decoder (errors, crashes, a structurally invalid btree), or corruption of the heap or of the WAL itself. Logical decoding reads the WAL; if the WAL or the heap page is damaged, none of this applies. The only fault tested is a consistent but wrong index.
- Other corruption methods and other ways the heap and index can disagree (HOT chains, deduplication posting lists, a unique index, partial or expression indexes, a collation change). One method, one index shape (non-unique btree on an `int`).
- Other PostgreSQL versions, other output plugins, other decoders (`wal2json`, `test_decoding`), other Debezium versions or connector settings.
- Other replica identities: `REPLICA IDENTITY USING INDEX` (including with the corrupted index as the identity index, which would be a different and more worrying case), and `NOTHING`.
- Nullable columns, TOASTed columns that are not part of the change, arrays, enums, generated columns, partitioned tables, tables with triggers or foreign keys that the DELETE cascades through.
- Scale and concurrency: 30 rows per table, one DELETE per table, one session, nothing else writing. No concurrent writers, no long transaction, no large delete.
- A durable store of the events, and the event retention a real repair would need. Events were kept in a file in a pod.
- Whether the events would have given Matrix their victim list "immediately", or in less than the week they spent. It would have required `REPLICA IDENTITY FULL` (or knowing the keys), a consumer retained since before the incident, and knowing which transactions were the clean-up job; none of that is known about their system.
- Added after the runs:
  - The default-identity before image of tables with nullable columns, and any statement about how often the placeholder trap would bite in a real schema.
  - Cost: `REPLICA IDENTITY FULL` makes events carry the row twice (see `repair-from-stream` and `replica-identity-full-cost`). Event sizes were not examined here.
  - The 16 table-runs are four repetitions of a deterministic construction over 4 tables, not 16 independent tests.
